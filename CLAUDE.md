## Product

Kkomkkomi (꼼꼬미) is a mobile app for small cleaning companies in Korea: teams of one to five people that clean offices and shops on a recurring schedule.
A worker selects a client and a visit date, takes paired before/after photos for each saved zone, adds notes, and shares a completion report that carries the company logo.
The next visit loads the same zone list and the previous photos.
The source of this section is the business plan dated 2026-10-01, which is not checked in.

### Product rules that constrain code

- The web link is the primary report output, opened from KakaoTalk. PDF and image are secondary outputs, and the PDF is generated on the device and sent through the OS share sheet.
- Each client has a fixed report URL with a cumulative history page. The plan treats this history as the reason a company stays, so do not design reports as one-off files.
- A link open is not a confirmation. Show a link open as "열람됨" only, and show "담당자 확인" only after the recipient presses the confirm button inside the report.
- A report URL is hard to guess but not private. The plan requires link expiry, reissue, and per-client access removal, and it requires the app to tell the company that anyone with the link can open the report.
- Photos can show faces, monitors, and documents. The plan lists a caution in the capture guide and a masking tool before upload as items to evaluate, and the legal scope under the Korean privacy law is an open question to settle before release.
- Field networks are unreliable. Upload retry and compression of large photos are the two technical risks the plan names.
- User-facing copy presents only the features of shipped milestones as available and marks later features as "예정".

## Commands

`merry.yaml` owns the local scripts and their definitions, and `merry ls` lists them.

```sh
# Local gate: format check, analyze, bloc lint, test, web report page test
merry run check

# Coverage under the CI threshold
merry run coverage

# Security rules tests in the Firebase emulators (needs Java 21 and the Firebase CLI)
merry run rules

# Run a flavor (development, staging, production)
merry run dev

# Regenerate localizations after an ARB edit
merry run l10n

# Regenerate lib/gen/assets.gen.dart after a change of the assets in pubspec.yaml
dart run build_runner build

# The web report page with fixture data, in Node (part of check)
merry run web

# The store screenshots and the Play feature graphic, then their check
CHROME=/path/to/chrome-headless-shell merry run store

# One test file, then one test by name
flutter test test/domain/client_test.dart
flutter test test/domain/client_test.dart --plain-name "trims the name"
```

The project has no `lib/main.dart`, so a bare `flutter run` fails.
`lib/gen/assets.gen.dart` is the FlutterGen output of the asset list in `pubspec.yaml`, and git tracks it. Code takes an asset path from `Assets` and never writes the path itself.
`build_runner` skips the generator while its cache is current, so when the file does not change after an asset change, run `dart run build_runner clean` first.
`lib/l10n/gen/` is ignored by git and generated from the ARB files.
`flutter pub get` generates it because `pubspec.yaml` sets `generate: true`.
When that directory is missing, `flutter analyze` reports `AppLocalizations` as undefined and does not regenerate it.

`merry run store` runs `tool/store_screenshots/render.sh`, which owns the steps and the output paths, and `tool/store_screenshots/check.sh` (`merry run store check`) owns the store sizes and the alpha check.
`CHROME` names the headless Chromium binary, the render needs ImageMagick 7, and the frames load Noto Sans KR from Google Fonts, so it also needs a network connection.
`render_screens.dart` pumps the real screens with fictional fixture data through the fakes of `test/helpers/`, in `flutter test` outside `test/`, so the suite, the coverage gate, and CI never run it.
The app bundles the regular and the bold weight of Noto Sans KR for the PDF, and `render_screens.dart` registers the regular file under every font family that the theme asks for, so the rendered screens draw every weight from it. The frames and the feature graphic load Noto Sans KR from Google Fonts at the weights that they use.

## CI

`.github/workflows/main.yaml` calls the Very Good reusable workflows for the title check, the Flutter gate, and the spell check, and it adds an Android build job, an iOS build job, and a Windows build job.

- Coverage must be 100% for `lib`, and CI counts only the files that a test imports. `merry run check` does not measure coverage, so run `merry run coverage` before a push.
- The pull request title must be a conventional commit.
- cspell checks every Markdown file and the pull request title against `cspell.json`. Project words go in `words` there, and general vocabulary goes in `.cspell/custom-dictionary.txt`.
- The `android` job builds the development debug APK. It cannot build a production variant, because those read `google-services.json`, which the repository does not hold, so no CI job checks the Firebase wiring or the release signing.
- The `ios` job builds the development debug app without signing on `macos-latest`, from a checkout without `GoogleService-Info.plist`. No CI job builds the production flavor of iOS, and no CI job builds macOS.
- The `windows` job is the only verification of the Windows build. Do not add a local Windows build script.
- The `web` job runs `test/web/` in Node, as `merry run web` does.
- The `rules` job runs `test/rules/` against the Firestore and Storage emulators with the project ID `demo-kkomkkomi`, as `merry run rules` does. `merry run check` leaves it out, because the emulators need Java 21. Firebase documents that a project ID with the `demo-` prefix reaches emulators only (https://firebase.google.com/docs/emulator-suite/connect_firestore, "Choose a Firebase project"), so never run the rules tests under another project ID.

Trunk installs a format hook on commit and a check hook on push (`.trunk/trunk.yaml`).

## Release

A release runs on the operator's machine with fastlane, and no CI job releases.
The root `Gemfile` pins fastlane (run `bundle install` once), `fastlane/Fastfile` holds the lanes, `fastlane/Appfile` holds the bundle ID, and `merry.yaml` owns the scripts that run them.

- `merry run release check` is offline. It fails for a working tree with uncommitted changes, for a version of `pubspec.yaml` without its entry in `CHANGELOG.md`, for a build number without `fastlane/metadata/android/<locale>/changelogs/<build>.txt` in each locale, for a store text that the metadata lanes upload when it is over its store limit in `tool/release_check.dart`, and when `config/revenuecat.json` is missing or does not hold each of its two keys as a string. The metadata lanes run it with `--metadata`, which leaves out the keys file, because they build nothing.
- `merry run build apk`, `merry run build aab`, and `merry run build ipa` read the RevenueCat public SDK keys from `config/revenuecat.json` with `--dart-define-from-file`, as `REVENUECAT_IOS_API_KEY` and `REVENUECAT_ANDROID_API_KEY`. Git ignores the file, so the keys are never tracked (operator, 2026-10-05), and `config/revenuecat.example.json` shows its two keys with empty values. A file with empty keys builds an app without subscriptions on purpose, and the release check of `release ios` and `release android` stops for a missing file, a file that is not a JSON object, and a missing or misspelled key, so that no build lacks the keys by accident.
- `merry run release ios` runs the check, checks the credentials, deletes `build/ios/ipa`, builds the production IPA, and uploads it to TestFlight. The upload lane stops for an IPA whose version and build number are not those of `pubspec.yaml`, because `flutter build ipa` exits 0 when the export of the IPA fails after the archive.
- `merry run release android` runs the check, checks the credentials, builds the production App Bundle, and uploads it with its changelogs to the internal testing track.
- `merry run release metadata ios` and `merry run release metadata android` run the check, so that a text over its store limit stops before the upload, and then upload the texts and images under `fastlane/metadata/` (and `fastlane/screenshots/ios` when it exists) without a binary and without a review submission. The Android lane needs a release on the internal testing track that holds the build number of `pubspec.yaml`, because `supply` stops before it uploads when it finds no release on the track that it is given.

The build number is an integer that grows by one for each upload, so bump `pubspec.yaml`, add the changelogs, and commit before a release.
iOS signs automatically with the `DEVELOPMENT_TEAM` of the Xcode project, without `match`.

## Architecture

The M1 design splits the code under `lib/` into units and owns the table of what each unit may import.
Each screen is a folder under `lib/presentation/` in the Very Good CLI layout: `cubit/` and `view/` subdirectories and a barrel file named after the screen.
Other code imports a unit or a screen through its barrel, for example `package:kkomkkomi/presentation/client_list/client_list.dart`.

- **Units.** `lib/domain/`, `lib/application/`, `lib/persistence/`, `lib/export/`, `lib/firebase/`, `lib/billing/`, and `lib/presentation/` exist, each with a barrel file named after the unit. `domain/` holds the entities and their rules, `Plan` among them, `application/` holds the repository interfaces, the `LocalDataRepository` that erases the whole database among them, the `Identity`, `Entitlements`, `ExternalLinks`, `IdGenerator`, `Clock`, `PhotoCapture`, `PhotoStore`, `ReportFont`, `ReportShare`, `LinkShare`, `Publisher`, and `NetworkMonitor` ports, the use cases, `DeleteAllData` among them, the `PublishQueue`, `reportLinkOf`, which makes the link of a report, and `withoutLocation`, which removes the location from a photo, and `persistence/` holds the version 5 SQLite schema, its upgrades from versions 1, 2, 3, and 4, and the `sqflite` repositories. `export/` holds the report document builder, the report file name, and the A4 PDF renderer. `firebase/` holds `FirebaseIdentity` and `FirebasePublisher`, the Firebase adapters of the `Identity` and `Publisher` ports. `billing/` holds `RevenueCatEntitlements`, the RevenueCat adapter of the `Entitlements` port, `PurchasesStore`, the one class that calls `purchases_flutter`, and `revenueCatEntitlementsFor`, which gives that adapter for iOS and Android when the key of the platform is not empty. The adapter configures RevenueCat with the Firebase user ID as the app user ID at its first call of any method that has a user ID, moves RevenueCat to a new user ID with `logIn`, shares one configuration between calls at one time, and gives the last plan that it knew for the current user ID, and Free before any answer for that ID, when RevenueCat or the identity fails. It sells the packages `basic_monthly`, `basic_annual`, `pro_monthly`, and `pro_annual` of the current offering, in that order, with the `priceString` of the store, and ignores any other package. On Google Play, `PurchasesStore` passes the subscription identifier of the Google Play subscription in use, without its base plan, as the product that a purchase replaces, because `basic` and `pro` are two Google Play subscriptions and a purchase without it would start a second one, with the replacement mode `withTimeProration` for a change to the other subscription and `chargeFullPrice` for a change of the base plan inside one subscription, which Google Play fails in any mode but `CHARGE_FULL_PRICE` and `WITHOUT_PRORATION`; a purchase does not start when that read fails. A purchase or a restore updates the known plan from the answer of the store and reports a change on `planChanges`; the error codes `purchaseCancelledError` and `paymentPendingError` give `cancelled` and `pending`, and every other failure gives `failed`. A `PlanOffer` is active when its store product grants an active entitlement; for Google Play the store also answers the subscription and base plan identifiers joined by a colon. `presentation/` holds one folder per screen, the adapters of the other nine ports, `UnavailableIdentity`, `UnavailablePublisher`, and `FreeEntitlements` (which sells nothing) under `adapters/`, and what more than one screen uses under `shared/`. `test/domain/boundary_test.dart` fails when a file under `lib/domain/` imports a library that the design does not allow. That rule excludes `package:meta`, so a domain file that overrides `==` carries an `ignore_for_file` comment for the lint that asks for `@immutable`.
- **Entry points.** `lib/main_development.dart`, `lib/main_staging.dart`, and `lib/main_production.dart` each call `bootstrap()` from `lib/bootstrap.dart`. `bootstrap()` installs the `FlutterError.onError` handler and `AppBlocObserver`, asks the `Identity` of the flavor for the user ID once, opens the database, and passes the repositories, that identity, the `Entitlements` of the flavor, and the publish queue to the builder that makes the app. It does not ask the entitlements for the plan. It does not wait for the answer of the identity, and a failure of the identity does not stop it. When the database is open, it starts a `PublishQueue` with the publisher of the flavor, and a failure of the queue does not stop it either. Before the queue starts, it runs `RecoverLostCapture`, and the builder gets what that step did, so that `App` opens the visit of a lost capture over the client list; a failure of the step is logged and the app opens on the client list. While the database does not open, it shows `StartupFailureApp`, and the retry control opens the database again. `App` provides the client, visit, company profile, and open capture repositories, the identity, the entitlements, the publish queue, the adapter of each other port that a screen uses, and one `DeleteAllData` for its whole life to the widgets below it through `RepositoryProvider`. The publish repository, the `Publisher`, and the `NetworkMonitor` go only to the queue, and the `LocalDataRepository` goes only to `DeleteAllData`. `App` has no default identity and no default entitlements, because the flavor decides them. The production entry point makes one `FirebaseIdentity` for `bootstrap()` and the RevenueCat adapter, and gives `FreeEntitlements` when `revenueCatEntitlementsFor` gives none; development and staging give `FreeEntitlements`. Configuration that all flavors share goes in `bootstrap()`, and configuration for one flavor goes in its `main_*.dart`.
- **Flavors.** Android defines them in `android/app/build.gradle.kts` with the application ID suffixes `.dev` and `.stg`. iOS and macOS define them as Xcode schemes. `windows/` has no flavor configuration, so a Windows build selects its entry point with `--target` alone. The `.vscode/launch.json` configurations pass the matching `--flavor` and `--target`.
- **Theme.** `appTheme()` in `lib/app/view/app_theme.dart` is the one theme, light only, and `App` and `StartupFailureApp` use it. Its color scheme takes the tokens of `web/index.html` for the roles that match one and generates the others from the teal, and a dialog sits on white because the teal of a text button is under 4.5:1 on the generated dialog color. `test/app/view/app_theme_test.dart` fails when a pair of colors that carries text is under 4.5:1. `showConfirmDialog` takes `isDestructive` for an action that deletes data, closes a link, or loses a note, and a `Notice` from `lib/presentation/shared/` shows a message in the info tone or a failure in the error tone.
- **State.** Each page widget creates its Cubit in a `BlocProvider` and renders a separate view widget that reads it, as `ClientListPage` and `ClientListView` do. This split lets a widget test inject a mock Cubit into the view. A state is one final class with a status enum and hand-written equality, in a `part` file of its Cubit, and every state but `ReportLinkState` has `copyWith`. A Cubit turns a `DomainException` into a `NameEntry` value in its state, and `NameField` shows the message of that value under the field. A screen or a dialog that saves wraps itself in `SaveGuard`, which takes no touch and no back press while the change is on its way to storage, so that the answer finds the screen as the change left it.
- **Identity.** `Identity.currentUserId()` gives the ID of the current user, or null while identity is unavailable, and it does not throw. `FirebaseIdentity` calls `Firebase.initializeApp()` without options, which reads the native config file of the platform, and then gives the ID of the account that the device holds or signs in anonymously. A start or a sign-in that fails gives null, and the next call starts Firebase and signs in again. `bootstrap()` asks once, and the publish queue asks again before each job, so a job waits with its retry delay while identity is unavailable. `RevenueCatEntitlements` asks before each call, so after Delete All Data the release flavor also signs in with a new anonymous account when the plans screen reads the plan, or when the add control of the client list reads it at the Free limit, and the privacy pages say so in section 6. Calls at one time share one attempt. `Identity.deleteAccount()` deletes the account that the device holds and never signs in: no account, or one that the backend no longer has, counts as deleted. It first waits for a sign-in that is on its way, such as the one of the start of the app, so that the sign-in cannot make an account after the delete. The FlutterFire documentation of `User.delete` says that `requires-recent-login` does not apply to an anonymous user, and an anonymous account cannot sign in again to fix it, so that code is a failure of the deletion step like any other. `Identity.hasPaidEntitlement()` tells whether the current user holds a paid entitlement, and it does not throw. `FirebaseIdentity` waits for a sign-in that is on its way, never signs in, and reads the `revenueCatEntitlements` claim from `User.getIdTokenResult(true)`, a newly issued token at each call, so a claim that the extension removed after an expiry or a transfer does not survive in a cached token. Paid means a list that holds `basic` or `pro`, as `paid()` in `firestore.rules` reads it; no account, a missing network, and any failure give false. The Windows runner has no native config file, so there the start fails and identity stays unavailable. No build and no test checks the start of Firebase on a device: the tests replace `Firebase.initializeApp` and `FirebaseAuth` with fakes.
- **Photos.** `ImagePickerPhotoCapture` opens the camera app through `image_picker` and owns the size limit and the JPEG quality of a photo. `DocumentsPhotoStore` copies the picked file into `photos/<visitId>/` under the application documents directory, under a new name for each capture, and a `PhotoRef` holds the path relative to that directory. The copy goes through `withoutLocation`, which keeps the image data, the JFIF header, an ICC profile, and the Adobe segment, drops every other application segment (Exif, XMP, IPTC), every comment, and whatever follows the end of the image, and writes the Exif orientation back in a segment of its own, because both picker plugins leave the rotation in that tag and do not turn the pixels (issue 20). A file that is no well-formed JPEG makes the save fail with a `FormatException`, so the capture fails and the person takes the photo again. The publish queue and the PDF of the visit report run the function again on the bytes that they read, for a photo that an earlier version stored with its location; the queue stops such a job with `PublishFailure.photoNotJpeg` when the file is no well-formed JPEG. The file that the picker writes into the cache directory keeps the location on Android, and the one in the temporary directory can keep it on iOS. The files that an earlier version stored keep it on the device, and the objects that an earlier version uploaded keep it in Storage, because the queue does not upload a photo again that `published_photos` marks as arrived. `tool/photo_fixtures/make.py` makes the JPEG fixtures of these tests. `VisitCaptureCubit` sends the whole visit to the repository at each photo, each note edit, each status change, and each reason edit. A note edit does not wait for the save before it, so `VisitRepository.save` must apply saves in the order of the calls, and a capture waits for the answer to the newest save before it opens the camera. It deletes the file of a replaced photo only after storage took the new one. While storage does not hold a note, a status, or a reason, the screen keeps a notice with a control that saves again. The screen takes no back press while one of them is on its way to storage, and it asks before a person leaves with one that storage did not take. `ios/Runner/en.lproj/InfoPlist.strings` and `ios/Runner/ko.lproj/InfoPlist.strings` hold the camera usage description in English and in Korean, and `ios/Runner/Info.plist` keeps the Korean text as the fallback for a key that a strings file does not have. They also hold a photo library usage description, although the app never opens the photo library, because the `image_picker` README says that App Store policy requires the entry. Android needs no manifest entry, because the picker opens the camera app through an intent, and a `CAMERA` permission in the manifest would add a permission request that the flow does not need. Android can end the app while the camera app is open, and the photo of that capture then does not reach `takePhoto` (issue 7). So `VisitCaptureCubit` stores the visit, the zone, and the slot of a capture as the one row of `open_capture` before the camera opens, does not open the camera when storage does not take that row, and removes it when the camera answers in any way. At the next start, before the app runs, `RecoverLostCapture` reads that row, asks `PhotoCapture.retrieveLostPhoto`, which calls `retrieveLostData` of `image_picker`, keeps the file with `PhotoStore`, saves the visit, and removes the row. The plugin writes the lost answer on a background thread after the restart, so while the camera has no photo the step asks again for 2 seconds (`RecoverLostCapture.defaultRetryDelays`, an estimate that no device measured) and then keeps the row for the next start; a new capture clears the answer of the plugin and replaces the row, so a kept row never names another capture. A row for a visit or a zone record that does not exist, and any row where `PhotoCapture.keepsLostPhotos` is false (every platform but Android), is removed without asking the camera, and a camera that cannot be asked leaves the row for the next start. The visit screen then says whether the visit holds the photo. The design replaces the picker adapter with a camera preview inside the app in M2, which removes the camera app from the flow.

- **Publishing.** `PublishQueue` in `lib/application/` owns the order of the steps, the retries, and the job state, and `FirebasePublisher` only writes what the queue gives it. A client gets its page at its first publish: the page ID is 128 random bits from `newPageId`, stored in `client_pages`. A publish job writes the page, uploads each photo to `clientPages/<pageId>/<visitId>/<zoneId>-<slot>-<photo file name>.jpg`, then writes the report with the paths of its photos, never download URLs, and with the creation time of its job as `publishedAt`, and then deletes the objects of the visit that the report no longer names. Right before the report write, and at no other step and in no revoke job, the queue asks `Identity.hasPaidEntitlement()` and sets `PublishedReport.unbranded` from the answer, so a job that runs again after the plan ended writes the report with the footer. A check that does not answer within the step timeout gives the footer and not a retry, so the check never delays a job. `FirebasePublisher` writes `unbranded: true` only for an unbranded report and leaves the key out otherwise. When the rules refuse a report with the key, the same run writes it once more without the key, so the report appears with the footer; a refusal of that second write, and every other failure, ends the job as before. The name of the photo file is in the path because a retake is a new file, so an upload of the old photo that outlived its step timeout cannot replace the retake. `published_photos` records each object before its upload starts and marks it when the upload arrives, so a retry does not upload a photo again, and the cleanup after a report and a revoke delete every object that may exist, also one whose upload did not answer in time. An upload that does not answer within the step timeout is cancelled, and the queue waits up to the step timeout again for its end before the step counts as failed, so an upload does not outlive its job and create its object after a revoke deleted the path (issue 13). When the upload does not end in that wait either, the step fails, and while that upload is on its way no cleanup, revoke, or new upload acts on its object, so its record stays until a later run deletes the object. Known limit: a last request that the backend received before the cancel may still create the object after the client reports the cancel, and a delete that comes first then misses it. A job that fails for a reason that a retry can fix, a step that takes longer than `PublishQueue.defaultStepTimeout` included, runs again after a delay that doubles from 5 seconds up to 15 minutes. A job that fails for another reason stops with a `PublishFailure`, and `PublishQueue.updates` gives each change of a job for a screen to show. The queue runs every pending job at once at its start and when `NetworkMonitor.restored` reports a return of the network. `bootstrap()` makes the one queue of the app: a second queue on the same database would run the same job at the same time, so `bootstrap()` gives that instance to the builder, and `App` provides it to the screens. A run saves the result of a job only while the stored job is pending and of the generation that the run read, which a new publish request of the same visit increments, so neither a revoke nor a restart during a run is lost. A revoke marks the page as revoked on the backend and deletes the photos that the app uploaded under it, and a reissue revokes the old page and publishes each of its visits again under a new page. In the production flavor, the client detail screen says whether its client has an open link, and while it has one, it closes the link through `revokeClientPage` or replaces it through `reissueClientPage` after a confirmation. `ClientLinkCubit` reads inclusive pages from `PublishQueue.pagesOf` and revoke jobs from `revokeJobsOf` after job updates and client-specific `pageChanges`. An eligible open page has `revoked_at`, `server_delete_requested_at`, and `server_deleted_at` all null; this does not prove server existence. A completed revoke or confirmed deletion closes that page. Intent without confirmation warns that the previous link may still open. Confirmation suppresses only that page's pending/failed revoke warnings; a fresh open page retains its controls alongside warnings for other pages. The Cubit tracks an outstanding storage mutation separately from reads, and SaveGuard stays active until it settles, including a refresh failure. Dialogs describe only the current eligible link and include the earlier-page recovery warning when needed. A current read failure shows load failure and retry without stale controls; superseded read results and errors change nothing. The Korean label of the close is 링크 막기, because the dismiss button of every question says 닫기. The screen takes no touch and no back press only while the request is on its way to storage, not while the job runs. The revoke writes the revoke time stored with the local page, so a revoke job that runs again writes the same page. `firestore.rules` and `storage.rules` are the rules of the design, and `test/rules/` tests them in the emulators. `storage.rules` reads the page through `firestore.get`, which needs the IAM role that the Firebase CLI asks to grant at the first deploy of those rules.
- **Deletion.** `DeleteAllData` holds the one publish queue and waits for its active job, then calls `forgetArrivedUploads` so recorded photos are uploaded again by a later explicit share. `deletePublished` takes an inclusive snapshot of every `client_pages` row, including archived clients, revoked pages, and previously requested/confirmed deletion. It rejects unsettled uploads and unavailable identity before deleting. It stops all pending publish/revoke jobs with `PublishFailure.deletion` and emits only actual changed jobs. Deletion keeps all photos first, all reports second, and all pages third, because backend rules read the page to find its owner. Each page's own timed future contains the intent transaction, notifications, `deletePage`, confirmation transaction, and notifications. Both nullable INTEGER timestamps are first UTC microsecond values: `server_delete_requested_at` quarantines the page before the remote call; `server_deleted_at` records its acknowledgement. Each transaction stops that page's pending jobs and preserves revoked time and completed/failed history. Open selection, enqueue, revoke CAS, and common dispatch reject quarantined pages; dispatch checks before identity for both job kinds because a revoke backend write can recreate a missing page. The queue can accept a share while held, but cannot execute it. A later explicit share obtains a fresh page ID and publishes only the requested visit, with no historical republish or URL migration. Early photo/report failure does not create a new page intent. Intent alone does not prove removal, and startup never clears it or resumes whole-app deletion. Explicit Delete All Data retries every recorded page, including fresh pages created between attempts, and idempotent deletes preserve the first timestamps. No legacy job status supplies a deletion timestamp. Durable intent before the remote call quarantines an ID after process death or lost acknowledgement; a confirmed timestamp cannot make backend and SQLite writes atomic. A confirmation failure stops before account/device deletion, and explicit retry reconciles the page. `pageChanges` invalidates its client after every committed intent/confirmation, even with zero stopped jobs. Disposal finishes durable writes without adding to closed streams. After published-data deletion, `Identity.deleteAccount` removes the anonymous account. Then `LocalDataRepository.eraseAll` deletes all rows in a transaction, runs `VACUUM` and a write-ahead-log checkpoint, and `PhotoStore.deleteAll` removes the photo folder. A transaction failure retains rows; VACUUM, checkpoint, or photo-file failure can happen after every row is gone. Company profile reports the actual stage failure separately from link state. Timeouts retain the entire combined future and hold until it settles; late page success still records confirmation but never resumes account/device stages automatically. A late account success keeps the queue held, and the next explicit attempt finishes device erasure. Development/staging erase only device data. No production rule or Hosting deployment is authorized by these changes. Deletion does not cancel a store subscription and does not delete the RevenueCat customer record: the operator deletes that record by hand on request (operator, 2026-10-05), and the app calls no backend for it. `CompanyProfilePage` passes `PublishQueue.isAvailable` to `CompanyProfileView` as `mentionsStoreSubscription`, so the confirmation decides the production flavor without a call to `Entitlements`. With that flag on Android, the confirmation shows a notice with a link that opens `https://play.google.com/store/account/subscriptions` through `ExternalLinks` and shows the link failure notice of the plans screen inside the confirmation when the link does not open; on iOS it shows the notice with the steps in Settings and no link, because no Apple source for a subscriptions URL was found; on any other platform it shows no notice, because the app sells plans only on Android and iOS. `showConfirmDialog` takes the notice as its `details`.

## Conventions

- Material widgets come from `package:material_ui/material_ui.dart`. No file imports `package:flutter/material.dart`.
- Constructors are declared with `new` in place of the class name, for example `const new({super.key});`, and a class with an empty body ends with `;`. Keep this Dart 3.13 syntax and do not rewrite it to the older form.
- Lint rules are `very_good_analysis` plus `bloc_lint/recommended`, with the exceptions that `analysis_options.yaml` lists. The formatter page width is 120.
