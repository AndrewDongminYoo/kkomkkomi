## Product

Kkomkkomi (꼼꼬미) is a mobile app for small cleaning companies in Korea: teams of one to five people that clean offices and shops on a recurring schedule.
A worker selects a client and a visit date, takes paired before/after photos for each saved zone, adds notes, and shares a completion report that carries the company logo.
The next visit loads the same zone list and the previous photos.
The source of this section is the business plan dated 2026-10-01, which is not checked in.

The repository is public while implementation is in progress, and the operator makes it private when the business starts (operator decision, 2026-10-01).

### Current state

The operator directed implementation to start on 2026-10-01, and M1 is the milestone in progress.
The data layer of the M1 build exists: the domain model, the repository interfaces and use cases, and the SQLite repositories.
The client list, the client detail, the visit capture, and the company profile screens use it, and the client list is the home screen.
The client detail screen starts a visit and opens a past one, and the visit capture screen takes the before photo, the after photo, and the note of each zone.
The visit capture screen opens the visit report screen, which previews the completion report and shares it as a PDF through the OS share sheet.

The publish queue publishes a visit as a report under the fixed page of its client and reads the user ID before each job, and in the production flavor the client detail screen closes the link of its client or replaces it with a new link.
The company profile screen deletes all data: what the app published, the anonymous account, and the data on the phone.
The stack is Flutter with Firebase (Auth, Firestore, Storage, Hosting), and the Firebase project is `kkomkkomi`.

### Product rules that constrain code

- The web link is the primary report output, opened from KakaoTalk. PDF and image are secondary outputs, and the PDF is generated on the device and sent through the OS share sheet.
- Each client has a fixed report URL with a cumulative history page. The plan treats this history as the reason a company stays, so do not design reports as one-off files.
- A link open is not a confirmation. Show a link open as "열람됨" only, and show "담당자 확인" only after the recipient presses the confirm button inside the report.
- A report URL is hard to guess but not private. The plan requires link expiry, reissue, and per-client access removal, and it requires the app to tell the company that anyone with the link can open the report.
- Photos can show faces, monitors, and documents. The plan lists a caution in the capture guide and a masking tool before upload as items to evaluate, and the legal scope under the Korean privacy law is an open question to settle before release.
- Field networks are unreliable. Upload retry and compression of large photos are the two technical risks the plan names.
- User-facing copy presents only the features of shipped milestones as available and marks later features as "예정".

## Architecture

The M1 design splits the code under `lib/` into units and owns the table of what each unit may import.
Each screen is a folder under `lib/presentation/` in the Very Good CLI layout: `cubit/` and `view/` subdirectories and a barrel file named after the screen.
Other code imports a unit or a screen through its barrel, for example `package:kkomkkomi/presentation/client_list/client_list.dart`.

- **Units.** `lib/domain/`, `lib/application/`, `lib/persistence/`, `lib/export/`, `lib/firebase/`, and `lib/presentation/` exist, each with a barrel file named after the unit. `domain/` holds the entities and their rules, `application/` holds the repository interfaces, the `LocalDataRepository` that erases the whole database among them, the `Identity`, `IdGenerator`, `Clock`, `PhotoCapture`, `PhotoStore`, `ReportFont`, `ReportShare`, `LinkShare`, `Publisher`, and `NetworkMonitor` ports, the use cases, `DeleteAllData` among them, the `PublishQueue`, `reportLinkOf`, which makes the link of a report, and `withoutLocation`, which removes the location from a photo, and `persistence/` holds the version 3 SQLite schema, its upgrades from versions 1 and 2, and the `sqflite` repositories. `export/` holds the report document builder, the report file name, and the A4 PDF renderer. `firebase/` holds `FirebaseIdentity` and `FirebasePublisher`, the Firebase adapters of the `Identity` and `Publisher` ports. `presentation/` holds one folder per screen, the adapters of the other eight ports, `UnavailableIdentity`, and `UnavailablePublisher` under `adapters/`, and what more than one screen uses under `shared/`. `test/domain/boundary_test.dart` fails when a file under `lib/domain/` imports a library that the design does not allow. That rule excludes `package:meta`, so a domain file that overrides `==` carries an `ignore_for_file` comment for the lint that asks for `@immutable`.
- **Entry points.** `lib/main_development.dart`, `lib/main_staging.dart`, and `lib/main_production.dart` each call `bootstrap()` from `lib/bootstrap.dart`. `bootstrap()` installs the `FlutterError.onError` handler and `AppBlocObserver`, asks the `Identity` of the flavor for the user ID once, opens the database, and passes the repositories, that identity, and the publish queue to the builder that makes the app. It does not wait for the answer of the identity, and a failure of the identity does not stop it. When the database is open, it starts a `PublishQueue` with the publisher of the flavor, and a failure of the queue does not stop it either. Before the queue starts, it runs `RecoverLostCapture`, and the builder gets what that step did, so that `App` opens the visit of a lost capture over the client list; a failure of the step is logged and the app opens on the client list. While the database does not open, it shows `StartupFailureApp`, and the retry control opens the database again. `App` provides each repository, the identity, the publish queue, the adapter of each other port, and one `DeleteAllData` for its whole life to the widgets below it through `RepositoryProvider`. `App` has no default identity, because the flavor decides it. Configuration that all flavors share goes in `bootstrap()`, and configuration for one flavor goes in its `main_*.dart`.
- **Flavors.** Android defines them in `android/app/build.gradle.kts` with the application ID suffixes `.dev` and `.stg`. iOS and macOS define them as Xcode schemes. `windows/` has no flavor configuration, so a Windows build selects its entry point with `--target` alone. The `.vscode/launch.json` configurations pass the matching `--flavor` and `--target`.
- **State.** Each page widget creates its Cubit in a `BlocProvider` and renders a separate view widget that reads it, as `ClientListPage` and `ClientListView` do. This split lets a widget test inject a mock Cubit into the view. A state is one final class with a status enum, `copyWith`, and hand-written equality, in a `part` file of its Cubit. A Cubit turns a `DomainException` into a `NameEntry` value in its state, and `NameField` shows the message of that value under the field. A screen or a dialog that saves wraps itself in `SaveGuard`, which takes no touch and no back press while the change is on its way to storage, so that the answer finds the screen as the change left it.
- **Identity.** `Identity.currentUserId()` gives the ID of the current user, or null while identity is unavailable, and it does not throw. `FirebaseIdentity` calls `Firebase.initializeApp()` without options, which reads the native config file of the platform, and then gives the ID of the account that the device holds or signs in anonymously. A start or a sign-in that fails gives null, and the next call starts Firebase and signs in again. `bootstrap()` asks once, and the publish queue asks again before each job, so a job waits with its retry delay while identity is unavailable. Calls at one time share one attempt. `Identity.deleteAccount()` deletes the account that the device holds and never signs in: no account, or one that the backend no longer has, counts as deleted. It first waits for a sign-in that is on its way, such as the one of the start of the app, so that the sign-in cannot make an account after the delete. The FlutterFire documentation of `User.delete` says that `requires-recent-login` does not apply to an anonymous user, and an anonymous account cannot sign in again to fix it, so that code is a failure of the deletion step like any other. The Windows runner has no native config file, so there the start fails and identity stays unavailable. No build and no test checks the start of Firebase on a device: the tests replace `Firebase.initializeApp` and `FirebaseAuth` with fakes.
- **Photos.** `ImagePickerPhotoCapture` opens the camera app through `image_picker` and owns the size limit and the JPEG quality of a photo. `DocumentsPhotoStore` copies the picked file into `photos/<visitId>/` under the application documents directory, under a new name for each capture, and a `PhotoRef` holds the path relative to that directory. The copy goes through `withoutLocation`, which keeps the image data, the JFIF header, an ICC profile, and the Adobe segment, drops every other application segment (Exif, XMP, IPTC), every comment, and whatever follows the end of the image, and writes the Exif orientation back in a segment of its own, because both picker plugins leave the rotation in that tag and do not turn the pixels (issue 20). A file that is no well-formed JPEG makes the save fail with a `FormatException`, so the capture fails and the person takes the photo again. The publish queue and the PDF of the visit report run the function again on the bytes that they read, for a photo that an earlier version stored with its location; the queue stops such a job with `PublishFailure.photoNotJpeg` when the file is no well-formed JPEG. The file that the picker writes into the cache directory keeps the location on Android, and the one in the temporary directory can keep it on iOS. The files that an earlier version stored keep it on the device, and the objects that an earlier version uploaded keep it in Storage, because the queue does not upload a photo again that `published_photos` marks as arrived. `tool/photo_fixtures/make.py` makes the JPEG fixtures of these tests. `VisitCaptureCubit` sends the whole visit to the repository at each photo and each note edit. A note edit does not wait for the save before it, so `VisitRepository.save` must apply saves in the order of the calls, and a capture waits for the answer to the newest save before it opens the camera. It deletes the file of a replaced photo only after storage took the new one. While storage does not hold a note, the screen keeps a notice with a control that saves again. The screen takes no back press while a note is on its way to storage, and it asks before a person leaves with a note that storage did not take. `ios/Runner/en.lproj/InfoPlist.strings` and `ios/Runner/ko.lproj/InfoPlist.strings` hold the camera usage description in English and in Korean, and `ios/Runner/Info.plist` keeps the Korean text as the fallback for a key that a strings file does not have. They also hold a photo library usage description, although the app never opens the photo library, because the `image_picker` README says that App Store policy requires the entry. Android needs no manifest entry, because the picker opens the camera app through an intent, and a `CAMERA` permission in the manifest would add a permission request that the flow does not need. Android can end the app while the camera app is open, and the photo of that capture then does not reach `takePhoto` (issue 7). So `VisitCaptureCubit` stores the visit, the zone, and the slot of a capture as the one row of `open_capture` before the camera opens, does not open the camera when storage does not take that row, and removes it when the camera answers in any way. At the next start, before the app runs, `RecoverLostCapture` reads that row, asks `PhotoCapture.retrieveLostPhoto`, which calls `retrieveLostData` of `image_picker`, keeps the file with `PhotoStore`, saves the visit, and removes the row. The plugin writes the lost answer on a background thread after the restart, so while the camera has no photo the step asks again for 2 seconds (`RecoverLostCapture.defaultRetryDelays`, an estimate that no device measured) and then keeps the row for the next start; a new capture clears the answer of the plugin and replaces the row, so a kept row never names another capture. A row for a visit or a zone record that does not exist, and any row where `PhotoCapture.keepsLostPhotos` is false (every platform but Android), is removed without asking the camera, and a camera that cannot be asked leaves the row for the next start. The visit screen then says whether the visit holds the photo. The design replaces the picker adapter with a camera preview inside the app in M2, which removes the camera app from the flow.
- **Report.** `ReportDocument.fromVisit` in `lib/export/` builds what a report prints from a visit, its client, and the company profile, and it leaves out a zone record without a photo and without a note. A zone record without a photo and with a note stays, with two empty slots. The preview of the visit report screen and `renderReportPdf` both show that document, so they hold the same zones, and both show the whole of each photo in a slot of the ratio `reportSlotAspectRatio`. `lib/export/` imports only the domain and `package:pdf`, and no Flutter library, and `test/export/boundary_test.dart` fails when a file there imports another library. So the caller gives the renderer what needs Flutter or a file: the texts as a `ReportLabels` value from the ARB files, the font bytes from the `ReportFont` port, and the photo bytes from `PhotoStore.read`. `PrintingReportShare` is the one file under `lib/` that imports `printing`, and `test/presentation/printing_import_test.dart` fails when a second file imports it. On Android and iOS the plugin answers when the share sheet opens, so the app does not know whether the person sent the file. The plugin writes the file under the name that it is given, and a name that the file system refuses makes the share do nothing without an error, so `reportFileName` removes the characters that a file name cannot hold and limits each part in UTF-8 bytes. `VisitReportCubit.share` catches every object, because `pdf` holds code that throws objects that are no exception, such as the `String` of `PdfJpegInfo`, and the screen takes no touch while a share is on its way. The PDF is rendered on the UI isolate. `assets/fonts/NotoSansKR-Regular.ttf` is the font of the PDF, with its license in `assets/fonts/OFL.txt`. It is the regular weight of the variable Noto Sans KR font, made with `fonttools varLib.instancer NotoSansKR.ttf wght=400 --update-name-table`, because `pdf` reads no weight axis and prints a variable font at its lightest weight. A character that the font does not have, such as an emoji, prints as a crossed box. Known limits, which the adapter cannot see: when the plugin cannot write the file, no share sheet opens and the call still answers that it did, and on Android the plugin leaves each shared file in the cache directory of the app, where only the end of the app process or the system removes it.
- **Publishing.** `PublishQueue` in `lib/application/` owns the order of the steps, the retries, and the job state, and `FirebasePublisher` only writes what the queue gives it. A client gets its page at its first publish: the page ID is 128 random bits from `newPageId`, stored in `client_pages`. A publish job writes the page, uploads each photo to `clientPages/<pageId>/<visitId>/<zoneId>-<slot>-<photo file name>.jpg`, then writes the report with the paths of its photos, never download URLs, and with the creation time of its job as `publishedAt`, and then deletes the objects of the visit that the report no longer names. The name of the photo file is in the path because a retake is a new file, so an upload of the old photo that outlived its step timeout cannot replace the retake. `published_photos` records each object before its upload starts and marks it when the upload arrives, so a retry does not upload a photo again, and the cleanup after a report and a revoke delete every object that may exist, also one whose upload did not answer in time. An upload that does not answer within the step timeout is cancelled, and the queue waits up to the step timeout again for its end before the step counts as failed, so an upload does not outlive its job and create its object after a revoke deleted the path (issue 13). When the upload does not end in that wait either, the step fails, and while that upload is on its way no cleanup, revoke, or new upload acts on its object, so its record stays until a later run deletes the object. Known limit: a last request that the backend received before the cancel may still create the object after the client reports the cancel, and a delete that comes first then misses it. A job that fails for a reason that a retry can fix, a step that takes longer than `PublishQueue.defaultStepTimeout` included, runs again after a delay that doubles from 5 seconds up to 15 minutes. A job that fails for another reason stops with a `PublishFailure`, and `PublishQueue.updates` gives each change of a job for a screen to show. The queue runs every pending job at once at its start and when `NetworkMonitor.restored` reports a return of the network. `bootstrap()` makes the one queue of the app: a second queue on the same database would run the same job at the same time, so `bootstrap()` gives that instance to the builder, and `App` provides it to the screens. A run saves the result of a job only while the stored job is pending and of the generation that the run read, which a new publish request of the same visit increments, so neither a revoke nor a restart during a run is lost. A revoke marks the page as revoked on the backend and deletes the photos that the app uploaded under it, and a reissue revokes the old page and publishes each of its visits again under a new page. In the production flavor, the client detail screen says whether its client has an open link, and while it has one, it closes the link through `revokeClientPage` or replaces it through `reissueClientPage` after a confirmation. `ClientLinkCubit` reads the revoke jobs of the client from `PublishQueue.revokeJobsOf` again at each change in `PublishQueue.updates`, so the screen says that a link is closing while its revoke job is pending, a job that waits for a retry included, that it is closed only when the job is done, and that it did not close when the job stopped. A revoke job that the deletion of all data stopped with `PublishFailure.deletion` says instead that the deletion did not finish, because the deletion deletes the page after it stops the job. The Korean label of the close is 링크 막기, because the dismiss button of every question says 닫기. The screen takes no touch and no back press only while the request is on its way to storage, not while the job runs. The revoke writes the revoke time stored with the local page, so a revoke job that runs again writes the same page. `firestore.rules` and `storage.rules` are the rules of the design, and `test/rules/` tests them in the emulators. `storage.rules` reads the page through `firestore.get`, which needs the IAM role that the Firebase CLI asks to grant at the first deploy of those rules.
- **Deletion.** `DeleteAllData` in `lib/application/` owns the order of the deletion of all data, and the company profile screen runs it after a confirmation. It holds the publish queue first: `PublishQueue.hold` waits for the job that runs now and starts no other job until `release`. Its first step, before any delete, is `PublishQueue.forgetArrivedUploads`, which marks every `published_photos` row as not arrived in one transaction and keeps the rows: a publish skips the upload of a photo whose row says that it arrived, and a deletion can make that row false (a delete that answers late, a row whose removal fails after its object went), so from then on the next share uploads every photo again, and an upload of the same path is safe to repeat. Then `PublishQueue.deletePublished` deletes, for every page in `client_pages`, open and revoked, the objects that `published_photos` records, uploads that did not arrive included, then the report of every visit that a job of the page names, then the page. It fails before any delete while an upload that a cancel did not end is on its way (issue 13), or while no user is signed in. Before its first delete, it stops every pending job, publish and revoke, with `PublishFailure.deletion` in `publish_jobs`, because a delete whose answer did not arrive may still have reached the backend, and a job that ran after a failure or at the next start would publish again what the deletion removed; the stopped jobs keep their rows, so a retry still finds every report to delete. Then `Identity.deleteAccount` deletes the account, and only then `LocalDataRepository.eraseAll` deletes every row in one transaction, runs `VACUUM` so that the file keeps no deleted bytes, and `PhotoStore.deleteAll` deletes `photos/`. A step that fails stops the deletion, and the screen names the step. Each try runs every step again, because a share between two tries can publish again, and each step is safe to repeat; a try after the account is gone signs in with a new account, whose deletes of what is gone the rules allow, and deletes that account too. The queue is released when the deletion ends, completed or failed, so only a share that the person starts again publishes after a failed deletion, and it recreates the page with that report. The one exception is a delete of the backend that did not answer within the step timeout, whether of a photo object, a report, a page, or the account: the timeout does not cancel it, so `DeleteAllData` keeps every such future in one place, as the queue keeps an upload that a cancel did not end (issue 13), and the queue stays held until all of them ended. A late photo delete could otherwise land after a share in the meantime uploaded the photo again to the same path, and remove the object that the new report names; its row stays as an intent, which a next try deletes again. A late account delete could otherwise remove the user ID that such a share published under; when it ends with success, the queue stays held and the next try erases the device only. A late report or page delete conflicts with no write, because the Firestore client sends its writes in order, and it is kept all the same. A try while any of them runs starts no second delete, waits for all of them as long as a step may take, and names the earliest step still on its way when one does not end. The objects go first because the Storage rules read the page to find the owner, and the reports before their page for the same reason in the Firestore rules. A delete of a page or a report that does not exist is allowed for any signed-in user, so a retry after a delete whose answer was lost is not refused. In the development and staging flavors, the deletion erases the data on the phone only. After a deletion the client list reads its empty list again, and the next start or publish signs in with a new anonymous account. What stays after a deletion is in section 6 of the privacy pages.
- **Navigation.** No router package exists. A page has a static `route()` that makes a `MaterialPageRoute`, and a widget opens it with `Navigator.push`.
- **Web.** No Flutter web app is planned. `web/` is the deploy root of the static landing page, which lives in this repository and not in a separate one, and `web/index.html` is that page (operator decision, 2026-10-01). It is one hand-written HTML file, so no Flutter build produces or checks it. `web/og.png` and the two icons under `web/icons/` are renders of the cards under `tool/web_assets/`, and `tool/web_assets/render.sh` owns how to make them again. Firebase Hosting serves `web/` at `https://kkomkkomi.web.app`, and `firebase deploy --only hosting` publishes it. A deploy, and a change to the deployed security rules, needs the operator's approval each time. The web report page is `web/report/index.html` with its script and style beside it, plain files without a build step, and `firebase.json` rewrites every path under `/r/` to it: `/r/<pageId>/<visitId>` shows one report and `/r/<pageId>` the list of the reports of the client page. It reads the configuration of the project from the reserved Hosting path `/__/firebase/init.json`, so no tracked file holds it, and it loads no Firebase SDK, because `/__/firebase/init.js` initializes only the SDK of version 8 and earlier (https://firebase.google.com/docs/hosting/reserved-urls). It reads the documents through the Firestore REST API and each photo from the Storage REST API without a download token, so the rules check every read, and a revoked or unknown page ID shows one message. It puts every text from the backend into `textContent`. `test/web/` tests it in Node with fixture data and a fake document (`merry run web`), and `test/rules/web_report.test.js` tests its reads in the emulators. The visit report screen shares the link only after the publish job of the visit is done, so a shared link never opens a page or a report that the backend does not hold, and it opens the share sheet then only while it is on top and no PDF share is on its way, else the next press publishes again and shares, and it tells the person at the first link of a client that anyone with the link can open the reports. `share_plus` opens the share sheet for the link, through `SharePlusLinkShare`. The privacy policy is `web/privacy/index.html` in Korean at `/privacy/` and `web/privacy/en/index.html` in English at `/privacy/en/`, plain HTML with one style sheet and no script, and the footer of the web report page links to it. Each clause states what the code, the rules, or a command output shows, and the pull request that added the pages lists the source of each clause. A change to what the app keeps, sends, shows, or deletes updates both pages together. `test/web/privacy.test.mjs` checks the files of the pages in Node, which measures no layout.
- **App icon.** `tool/app_icon/symbol.svg` is the master of the mark, and `tool/app_icon/render.sh` owns the list of the files that hold a copy of it and makes the legacy Android images, the launch images, and the Windows icon. Android uses an adaptive icon in each source set, and iOS and macOS use the Icon Composer bundles under `ios/Runner/AppIcons/` and `macos/AppIcons/`. The development and staging icons carry a label. The launch screen of Android and iOS shows the icon on a white ground, because the first screen of the app is light.
- **Localization.** All user-facing strings come from `lib/l10n/arb/` through `context.l10n`, which `lib/l10n/l10n.dart` defines. `app_en.arb` is the template and `app_ko.arb` is the Korean locale, so each new key goes in both files. A new locale also needs an entry in `CFBundleLocalizations` in `ios/Runner/Info.plist`, and an `InfoPlist.strings` under `ios/Runner/<locale>.lproj/` in the `InfoPlist.strings` variant group of the Runner target. Every `MaterialApp` takes `appLocalizationsDelegates` from `lib/l10n/l10n.dart`, because the generated `AppLocalizations.localizationsDelegates` does not serve the widgets of `material_ui`.
- **Tests.** `test/` mirrors `lib/`. Widget tests use `tester.pumpApp()` from `test/helpers/`, which wraps the widget in a `MaterialApp` with the localization delegates. Cubit tests use `blocTest`, and view tests mock the Cubit with `MockCubit` from `bloc_test` and stub it with `mocktail`. Repository tests run the `sqflite` repositories against `sqflite_common_ffi`, and `test/persistence/support.dart` opens the in-memory database that they use. `mockRepositories()` from `test/helpers/` gives a widget test repositories that never reach a database. A page test passes the in-memory repositories of `test/helpers/fakes.dart` to `pumpApp`, which then provides what `App` provides. `FakePhotoCapture` and `FakePhotoStore` from the same file replace the camera and the photo files, `FakeOpenCaptureRepository` replaces the stored open capture, and `FakeReportShare` and `FakeLinkShare` replace the share sheet, so no screen test touches a platform channel. `FakeIdentity` replaces the identity, `FakePublisher` and `FakeNetworkMonitor` replace the backend and the network state, `FakeLocalDataRepository` replaces the erase of the database, and no test starts Firebase. The queue tests run `PublishQueue` against the in-memory SQLite repositories. A widget test runs in fake time, where the database does not answer, so a screen test that runs the queue uses `FakePublishRepository`, and `publishQueueOf()` makes a queue over the repositories of a test, without a backend unless the test gives one. `FileReportFont` reads the font file from the source tree, so a screen test renders the PDF, and `PdfSummary` from `test/helpers/` reads the size, the text, and the images of each page of the result. `PdfSummary` is not a PDF library: it follows the cross-reference stream to the catalog, the page tree, and each page, decodes the compressed streams on that path, and reads only the forms that the `pdf` package writes. A photo on the screen is a `PhotoThumbnail`, and `tester.photoPathsIn()` reads the file paths that the thumbnails show, because the fake photo store holds no file to show. `tester.useNarrowScreenWithLargestText()` sets the 320 pixel width and the largest text size at which no screen may overflow, and `tester.expectWholeText()` fails for text that the framework cuts without an overflow error.

## Conventions

- Material widgets come from `package:material_ui/material_ui.dart`. No file imports `package:flutter/material.dart`.
- Constructors are declared with `new` in place of the class name, for example `const new({super.key});`, and a class with an empty body ends with `;`. Keep this Dart 3.13 syntax and do not rewrite it to the older form.
- Lint rules are `very_good_analysis` plus `bloc_lint/recommended`, with the exceptions that `analysis_options.yaml` lists. The formatter page width is 120.
