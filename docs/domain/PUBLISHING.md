# Publishing

Moved unchanged from `CLAUDE.md` § Architecture on 2026-11-02.

- **Publishing.** `PublishQueue` in `lib/application/` owns the order of the steps, the retries, and the job state, and `FirebasePublisher` only writes what the queue gives it. A client gets its page at its first publish: the page ID is 128 random bits from `newPageId`, stored in `client_pages`. A publish job writes the page, uploads each photo to `clientPages/<pageId>/<visitId>/<zoneId>-<slot>-<photo file name>.jpg`, then writes the report with the paths of its photos, never download URLs, and with the creation time of its job as `publishedAt`, and then deletes the objects of the visit that the report no longer names. Right before the report write, and in no revoke job, the queue asks `Identity.hasPaidEntitlement()` and sets `PublishedReport.unbranded` from the answer, so a job that runs again after the plan ended writes the report with the footer. A check that does not answer within the step timeout gives the footer and not a retry, so the check never delays a job. `FirebasePublisher` writes `unbranded: true` only for an unbranded report and leaves the key out otherwise. When the rules refuse a report with the key, the same run writes it once more without the key, so the report appears with the footer; a refusal of that second write, and every other failure, ends the job as before. The name of the photo file is in the path because a retake is a new file, so an upload of the old photo that outlived its step timeout cannot replace the retake. `published_photos` records each object before its upload starts and marks it when the upload arrives, so a retry does not upload a photo again, and the cleanup after a report and a revoke delete every object that may exist, also one whose upload did not answer in time. An upload that does not answer within the step timeout is cancelled, and the queue waits up to the step timeout again for its end before the step counts as failed, so an upload does not outlive its job and create its object after a revoke deleted the path (issue 13). When the upload does not end in that wait either, the step fails, and while that upload is on its way no cleanup, revoke, or new upload acts on its object, so its record stays until a later run deletes the object. Known limit: a last request that the backend received before the cancel may still create the object after the client reports the cancel, and a delete that comes first then misses it. A job that fails for a reason that a retry can fix, a step that takes longer than `PublishQueue.defaultStepTimeout` included, runs again after a delay that doubles from 5 seconds up to 15 minutes. A job that fails for another reason stops with a `PublishFailure`, and `PublishQueue.updates` gives each change of a job for a screen to show. When a publish job fails with `PublishErrorKind.unapproved`, which `FirebasePublisher` throws for a missing or disabled grant, the queue also asks `Identity.hasPaidEntitlement()`; for a paid user it calls `Publisher.createOwnGrant` as a write of its own and runs the job once more, and otherwise the job stops as `refused` (`docs/specs/2026-11-02-publisher-approval-request.md`). After a refused share, `ReportLinkCubit` reads `publishingRequests/{uid}` through `PublishQueue.hasApprovalRequest`, and the visit report screen sends a request through `PublishQueue.requestApproval` or shows it as pending. `FirebasePublisher` cuts a saved company name to the 100 characters that the rules take in a request. The queue runs every pending job at once at its start and when `NetworkMonitor.restored` reports a return of the network. `bootstrap()` makes the one queue of the app: a second queue on the same database would run the same job at the same time, so `bootstrap()` gives that instance to the builder, and `App` provides it to the screens. A run saves the result of a job only while the stored job is pending and of the generation that the run read, which a new publish request of the same visit increments, so neither a revoke nor a restart during a run is lost. A revoke marks the page as revoked on the backend and deletes the photos that the app uploaded under it, and a reissue revokes the old page and publishes each of its visits again under a new page. In the production flavor, the client detail screen says whether its client has an open link, and while it has one, it closes the link through `revokeClientPage` or replaces it through `reissueClientPage` after a confirmation. `ClientLinkCubit` reads inclusive pages from `PublishQueue.pagesOf` and revoke jobs from `revokeJobsOf` after job updates and client-specific `pageChanges`. An eligible open page has `revoked_at`, `server_delete_requested_at`, and `server_deleted_at` all null; this does not prove server existence. A completed revoke or confirmed deletion closes that page. Intent without confirmation warns that the previous link may still open. Confirmation suppresses only that page's pending/failed revoke warnings; a fresh open page retains its controls alongside warnings for other pages. The Cubit tracks an outstanding storage mutation separately from reads, and SaveGuard stays active until it settles, including a refresh failure. Dialogs describe only the current eligible link and include the earlier-page recovery warning when needed. A current read failure shows load failure and retry without stale controls; superseded read results and errors change nothing. The Korean label of the close is 링크 막기, because the dismiss button of every question says 닫기. The screen takes no touch and no back press only while the request is on its way to storage, not while the job runs. The revoke writes the revoke time stored with the local page, so a revoke job that runs again writes the same page. `firestore.rules` and `storage.rules` are the rules of the design, and `test/rules/` tests them in the emulators. `storage.rules` reads the page through `firestore.get`, which needs the IAM role that the Firebase CLI asks to grant at the first deploy of those rules.
