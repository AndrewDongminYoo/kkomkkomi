# Deletion

Moved unchanged from `CLAUDE.md` § Architecture on 2026-11-02.

- **Deletion.** `DeleteAllData` holds the one publish queue and waits for its active job, then calls `forgetArrivedUploads` so recorded photos are uploaded again by a later explicit share. `deletePublished` takes an inclusive snapshot of every `client_pages` row, including archived clients, revoked pages, and previously requested/confirmed deletion. It rejects unsettled uploads and unavailable identity before deleting. It stops all pending publish/revoke jobs with `PublishFailure.deletion` and emits only actual changed jobs. Deletion keeps all photos first, all reports second, and all pages third, because backend rules read the page to find its owner. Each page's own timed future contains the intent transaction, notifications, `deletePage`, confirmation transaction, and notifications. Both nullable INTEGER timestamps are first UTC microsecond values: `server_delete_requested_at` quarantines the page before the remote call; `server_deleted_at` records its acknowledgement. Each transaction stops that page's pending jobs and preserves revoked time and completed/failed history. Open selection, enqueue, revoke CAS, and common dispatch reject quarantined pages; dispatch checks before identity for both job kinds because a revoke backend write can recreate a missing page. The queue can accept a share while held, but cannot execute it. A later explicit share obtains a fresh page ID and publishes only the requested visit, with no historical republish or URL migration. Early photo/report failure does not create a new page intent. Intent alone does not prove removal, and startup never clears it or resumes whole-app deletion. Explicit Delete All Data retries every recorded page, including fresh pages created between attempts, and idempotent deletes preserve the first timestamps. No legacy job status supplies a deletion timestamp. Durable intent before the remote call quarantines an ID after process death or lost acknowledgement; a confirmed timestamp cannot make backend and SQLite writes atomic. A confirmation failure stops before account/device deletion, and explicit retry reconciles the page. `pageChanges` invalidates its client after every committed intent/confirmation, even with zero stopped jobs. Disposal finishes durable writes without adding to closed streams. After published-data deletion, `Identity.deleteAccount` removes the anonymous account. The issue #86 approval and lifetime usage document remains until the operator deletes it on request, and durable page block IDs remain while the service operates; both privacy pages disclose these exceptions. Then `LocalDataRepository.eraseAll` deletes all rows in a transaction, runs `VACUUM` and a write-ahead-log checkpoint, and `PhotoStore.deleteAll` removes the photo folder. A transaction failure retains rows; VACUUM, checkpoint, or photo-file failure can happen after every row is gone. Company profile reports the actual stage failure separately from link state. Timeouts retain the entire combined future and hold until it settles; late page success still records confirmation but never resumes account/device stages automatically. A late account success keeps the queue held, and the next explicit attempt finishes device erasure. Development/staging erase only device data. No production rule or Hosting deployment is authorized by these changes. Deletion does not cancel a store subscription and does not delete the RevenueCat customer record: the operator deletes that record by hand on request (operator, 2026-10-05), and the app calls no backend for it. `CompanyProfilePage` passes `PublishQueue.isAvailable` to `CompanyProfileView` as `mentionsStoreSubscription`, so the confirmation decides the production flavor without a call to `Entitlements`. With that flag on Android, the confirmation shows a notice with a link that opens `https://play.google.com/store/account/subscriptions` through `ExternalLinks` and shows the link failure notice of the plans screen inside the confirmation when the link does not open; on iOS it shows the notice with the steps in Settings and no link, because no Apple source for a subscriptions URL was found; on any other platform it shows no notice, because the app sells plans only on Android and iOS. `showConfirmDialog` takes the notice as its `details`.
