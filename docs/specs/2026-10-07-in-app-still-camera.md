# In-app still camera for capture time (#61)

Date: 2026-10-07. Status: draft for written review; no camera code is implemented by this document.

## Purpose and existing contracts

Let a worker take one before or after photo inside the app, with an app-observed capture instant that appears in the PDF and report preview. This completes the missing camera producer of [#61](https://github.com/AndrewDongminYoo/kkomkkomi/issues/61); PR #78 alone remains metadata foundation work.

The [M1 design](2026-10-01-m1-local-first-design.md), especially Units, Photos and Platforms, owns the architecture and mobile targets. Its M2 live-preview dependency is also recorded in [the gallery note](../notes/2026-10-03-gallery-photos-for-m2.md). The approved [metadata spec](2026-10-07-report-photo-and-company-metadata.md) and [plan](../plans/2026-10-07-approved-report-metadata.md) own source labels, nullable UTC storage, replacement rules and PDF/preview-only time captions. These decisions are retained.

## Recommended implementation

Use Flutter's `camera` plugin for the mobile preview and still image. The reviewed candidate is `camera` 0.12.1, with its endorsed Android and iOS implementations; record the resolved versions in the lockfile during implementation. [Its documentation](https://pub.dev/packages/camera) requires application-owned lifecycle handling and currently lists Android SDK 24+ and iOS 13+. Check these against the project's resolved build settings before installing it; do not silently raise supported OS versions.

The smallest alternative, if an actual sensor-exposure timestamp is required, is a native capture-event bridge on both platforms. That would require a revised spec and device validation; it is outside this proposal. Keeping the camera-app picker remains available on unsupported platforms but cannot complete #61.

### Exact observation event

When the initialized, foreground camera accepts a shutter press, acquire the single-capture guard, sample the injected `Clock.now().toUtc()` and immediately dispatch `takePicture()`, with no asynchronous wait between the sample and dispatch. Associate that observation only with the successful file from that operation and the same active session.

This is the app's observation of its shutter request, not a native sensor-exposure timestamp or independent proof of when work happened. [The standard `takePicture` API](https://pub.dev/documentation/camera/latest/camera/CameraController/takePicture.html) returns a file and exposes no exposure-time value in its signature or documented result. Never substitute its completion time, picker return time, file time, Exif, visit date or restart time. Failure, cancellation or session invalidation discards the observation. A retry observes a new request.

### Worker flow

1. The existing before/after take or retake action opens a separate in-app camera route on Android and iOS. The visit still waits for its pending edits and blocks competing changes as it does today.
2. Open the first available rear camera only when that route opens. If there is no rear camera, report the existing generic capture failure and preserve the photo. No camera enumeration or permission request occurs at app startup.
3. Show the live preview without stretching or cropping it, a localized camera title, one shutter control and a close/back control. Shutter stays disabled until ready and throughout capture. Use the current theme, `material_ui`, Korean and English ARB strings, `KeepAllText`, accessible labels and safe areas.
4. On successful capture and normalization, return the observed photo to the visit and save it immediately through the existing replacement flow. The returned visit thumbnail is the review surface; its existing retake action takes another photo. No separate use-photo confirmation screen is added.
5. Close/back cancels the session without changing the prior photo, source or time. Permission denial uses the existing capture-denied notice; missing hardware, initialization, capture or normalization failure uses the existing capture-failed notice. No automatic permission retry loop or settings-opening action is added.
6. The existing per-slot gallery action continues to use `image_picker`, with its provenance label and no capture time. Windows continues to build and uses the existing adapter without enumerating mobile camera hardware; Windows runtime camera support is not added.

No ghost overlay, front-camera switch, zoom/flash controls, video, audio, streaming, crop/edit controls, logo, tracking or report-slot ratio change joins this work. The live preview is a prerequisite of the wider M2 camera work, not completion of that wider milestone.

## Components and ownership

- Keep application and domain code independent of Flutter and the camera package. A presentation adapter implements `InAppPhotoCapture`; `takeObservedPhoto()` invokes an injected route-launch callback and returns the session result. `takePhoto()` delegates to the same session and returns its path. Gallery selection and Android lost-picker retrieval delegate to the existing picker adapter.
- `App` owns stable navigation/adapter wiring for its lifetime. Its mobile default selects the new composite adapter; explicit `PhotoCapture` injection in tests remains usable unchanged. `bootstrap()` retains picker-only lost-result recovery before the widget tree exists and never opens a preview.
- Add a `still_camera` presentation screen with the repository's page/view/Cubit layout. Its session owns readiness, capture state, generation and the injected clock. Its view owns the lifecycle listener and forwards lifecycle events to the session.
- Put camera-package calls behind one presentation driver boundary. It enumerates rear cameras, initializes a controller with `enableAudio: false`, supplies the preview widget, takes a still, and disposes resources. Tests replace this boundary and never open a real camera. The [controller API](https://pub.dev/documentation/camera/latest/camera/CameraController/CameraController.html) defaults audio to enabled, so passing false is explicit and tested.
- Camera temporary JPEG normalization uses the existing `image` dependency and a testable presentation helper. The session owns its raw/normalized temporary files until a successful result hands the normalized file to the visit. No application port gains a `BuildContext` or camera controller.

## Lifecycle, interruption and persistence

There is at most one active camera session and one capture operation. Serialize initialization, closing and replacement of controllers. Give each session/controller generation an identity so an obsolete initialization, capture or error cannot change a newer route, return a photo, or save a time.

On loss of foreground, disable capture, invalidate any pending capture result and release camera resources. On resume, recreate the preview only if its route is still active; no photo is taken automatically. Handle the initial permission dialog's inactive/resumed transitions without overlapping initialization or disposal; the first granted permission must reach a usable preview. Closing during initialization or capture resolves cancellation exactly once and ignores late answers. A subsequent session waits for previous resource closing to settle. Dispose the listener and controller on route exit; a late lifecycle event cannot reopen them.

The visit writes a new photo reference, source and UTC time together only after `PhotoStore.save` and the visit save succeed. Existing record data and the old file remain until then. Failed visit persistence removes the unused new file under the existing policy and retains the old record/time. A save already committed before process death remains committed; an interrupted uncommitted in-app session is cancelled and is not recovered from cached files.

`OpenCapture` remains an external-picker intent. Before an in-app camera session, clear any old `OpenCapture` row and do not create a new one; if clearing fails, do not open the camera and show save failure. This prevents a stale `image_picker` answer from being paired with an interrupted in-app session, without a schema change. Gallery still stores its source-bearing intent before opening the picker and uses the existing startup recovery. Old camera-picker intents from an earlier build can still recover as camera source with no time. Never mark the entire composite adapter as unable to recover lost photos, because that would lose Android gallery recovery. Closed issue #7 is retained as a regression contract, not reopened.

## Image and permission contract

- The new camera output must reach the existing save path as a well-formed JPEG, with the visible orientation preserved, aspect ratio retained, longest edge at most 1600 pixels and JPEG quality 80. Decode the camera JPEG, apply orientation to pixels, reduce it only when needed, encode, then apply `withoutLocation`. A resolution preset alone does not prove the size bound. The existing store, PDF and publish sanitization remain in force.
- Cancelled/obsolete sessions remove only temporary files that they own. Cleanup must not remove a file already handed to the visit, an existing report photo, or another session's file. Normalization failure leaves the previous photo intact.
- Camera access is requested only when the worker opens the preview. Android now needs camera permission, unlike the prior intent-only camera flow. Review the merged manifest: the upstream [CameraX manifest](https://github.com/flutter/packages/blob/main/packages/camera/camera_android_camerax/android/src/main/AndroidManifest.xml) also declares audio and legacy storage permissions. Remove `RECORD_AUDIO` and `WRITE_EXTERNAL_STORAGE` from the app's merged manifest, and keep camera hardware optional, because gallery-only use remains valid. Confirm these details against the versions actually resolved.
- iOS keeps accurate localized camera and gallery purpose strings. Do not add a microphone-purpose string or request microphone access for this still-only implementation. Confirm that the selected iOS implementation works with audio disabled and no microphone request; if it does not, fix or select a compatible implementation rather than expanding permission scope.
- Update both privacy pages together to describe the actual in-app, camera-only flow and app-observed local time. Photos continue through the existing publisher when the worker shares; capture time continues to be absent from public payloads and the web report. This code scope changes no Firebase rules, IAM, credentials or production settings.
